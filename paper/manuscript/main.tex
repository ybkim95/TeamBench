\title{What a Multi-Agent Coding Benchmark Measures When It Measures Nothing}
\author{Anonymous}
\date{}

\begin{document}
\maketitle

\begin{abstract}
We show that a multi-agent coding benchmark can report a complete set of
results while being unable to distinguish any two submissions, and we give a
protocol that detects this before any model is run. Applying it to our own
prior benchmark, 31 of 76 graders could not separate a correct submission from
an empty one, because the test that defines each bug is the one the upstream
pull request adds and the task ships the repository state from before it;
another 40 tasks shipped that test inside the workspace, handing the agent the
acceptance criterion. Two grader checks could not be satisfied by any
submission at all, including the maintainers' own merged fix. Across the
corpus, 303 of 374 checks pass on an untouched workspace, so 81\% of every
reported partial score was credit for not damaging the repository. We rebuild
the corpus by checking each task out from upstream at its recorded base commit
and injecting the held-out tests at grade time, admit only tasks that fail
without the reference fix and pass with it, and verify the result against seven
admission gates. On the 48 tasks that survive, we then re-run the comparison the
original paper could not settle: at matched compute a Planner/Executor/Verifier
team solved one task in 144 paired comparisons that a single agent failed, the
deficit widens as compute grows ($-0.104 \to -0.188$), and team runs damage the
workspace three times as often. On the scale the original paper used, none of
this is visible: a sevenfold compute increase moves the reported score by 1.5
points.
\end{abstract}

\section{Introduction}

A benchmark reports numbers whether or not it can measure anything. A grader
that awards the same score to every submission still produces a leaderboard, a
pass rate, and an ablation table. Nothing in the usual reporting pipeline
separates a task that is hard from a task that is inert.

This matters most where the expected effect is small. Whether decomposing a
software task across specialised agents helps at all is exactly such a question,
and the team performance literature has a long-standing answer to it.
\citet{steiner1972group} classifies group tasks by how individual contributions
combine, and predicts that on \emph{disjunctive} tasks, where one competent
member suffices, a group adds little over its strongest member. Coordination
gains instead require members to hold mutual knowledge of who knows what, a
transactive memory system \citep{wegner1987transactive,lewis2003measuring}, and
in software teams specifically that construct is among the more robust
correlates of performance \citep{faraj2000coordinating}. A benefit is expected
when members hold genuinely different information and must pool it
\citep{stasser1985pooling}.

So the prediction is available in advance: on tasks a single competent agent can
carry, a Planner/Executor/Verifier split should not help, and it should help
least when the roles cannot build mutual knowledge of each other. Recent work
reaches compatible conclusions empirically \citep{cemri2025why}. What has been
missing is an instrument sharp enough to test the prediction, because a null
result from a benchmark that cannot discriminate is not evidence of anything.

\paragraph{The instrument was broken, and specifically so.} We audited the
GitHub-derived half of our own prior benchmark. It was built by copying, for
each merged bug-fix pull request, the files that pull request touched, at the
commit before it. Two consequences follow, and they conceal each other.

First, the copied workspace is a fragment of a repository, so its test suite
cannot be collected: \texttt{conftest.py} is absent on 541 of the 553 tasks that
ship a test file, packages appear only in the pieces the diff touched, and
test-only dependencies are missing. The grader's central check fails for reasons
unrelated to any submission.

Second, and underneath it, the test that \emph{defines} the bug is the test the
pull request adds, and the commit before it does not contain that test. Of the
229 tasks whose reference patch adds a test, 189 ship the test file without the
added test, so the grader cannot separate any two submissions, and the remaining
40 ship the added test inside the workspace, so the agent can read the
acceptance criterion. The only tasks that could discriminate were the ones
leaking the answer. Applying the maintainers' own merged fix changed the reported
score on 3 of 153 tasks.

Two further grader checks could not be satisfied by any submission at all,
including the reference fix, and 303 of 374 checks pass on an untouched
workspace, so 81\% of every reported partial score was credit for not damaging
the repository.

\paragraph{An audit, not an assertion.} The obvious reading of the previous
paragraph is that we fixed our own bug. We answer that with a reusable
instrument. Five criteria, fixed in source before any external data was
downloaded, run unchanged over four corpora: three externally built and 1{,}800
instances between them clear every criterion, while our own corpus clears none
of 631. We report the scope of that result plainly in
Section~\ref{sec:related}: the three that pass share a construction in which the
discriminating test is held out by design, and corpora built outside that
lineage, including ours, do not inherit the property.

Calibrating the audit against benchmarks with no known defect was not a
formality. Before calibration it reported a 61\% false-positive rate, across
five distinct conventions for naming a test, and every one of those would have
been a public accusation against a sound benchmark. An audit that reports false
defects is worse than no audit, so ``undecidable'' is a first-class verdict here
rather than a rounding of ``failed''.

\paragraph{What the repaired instrument shows.} We rebuild the corpus by
checking each task out from upstream at its recorded base commit and injecting
the held-out tests at grade time, admit only tasks that fail without the
reference fix and pass with it, and verify the survivors against seven admission
gates. On the 48 tasks that remain we then run the comparison the original
version could not settle. Solo and a three-role team receive one shared turn
allowance, so the conditions are matched on compute rather than differing by a
factor of seven.

At equal compute the team solved one task in 144 paired comparisons that the
single agent failed. The deficit widens as the budget grows, from $-0.104$ to
$-0.188$, which closes off ``the team needs more compute'' as an explanation.
Team runs damage the workspace three times as often, rising with budget. And the
mechanism the theory points to is directly measurable: of 2{,}778 inter-role
messages, 99.0\% flow from Planner to Executor, and the Executor sent 2 messages
back to the Planner across 144 runs despite being instructed to report status.
The protocol is nominally bidirectional and empirically one-directional, so no
mutual knowledge of the kind \citet{faraj2000coordinating} identify can form.

None of this is visible on the scale the prior version reported: there a
sevenfold compute increase moves the score by 1.5 points and the two conditions
sit on top of each other.

\paragraph{Contributions.}
\begin{itemize}
\item \textbf{A validity audit for agentic benchmarks, calibrated against
      corpora that pass it.} Five criteria decidable from task metadata, a
      three-valued verdict, and a measured false-positive rate before and after
      calibration.
\item \textbf{Evidence that graders can be inert, quantified.} 31 of 76 graders
      could not see the bug until the held-out tests were injected; two check
      families could not be satisfied by the reference fix; 81\% of checks are
      guards that pass on an untouched workspace; 45 tasks have a reference
      patch that touches no source file.
\item \textbf{\core{}: 48 tasks that provably discriminate}, rebuilt from
      upstream with held-out tests and validated against seven gates.
\item \textbf{A compute-matched test of a decades-old prediction}, with a
      measured mechanism: the back-channel that mutual knowledge would require
      exists, is advertised in the prompt, and goes unused.
\end{itemize}

\section{How a grader becomes inert}
\label{sec:inert}

\paragraph{Setting.} Each task derives from a merged pull request that fixes a
bug. The task's workspace is the repository at the parent commit; the reference
solution is the merged diff. A grader runs a checklist and reports a pass flag
and a partial score.

\paragraph{The held-out test.} A bug-fix pull request usually adds the test that
demonstrates the bug. At the parent commit that test does not exist. A workspace
built from the parent commit therefore contains a test suite that passes, and
will keep passing whatever the agent does, unless the agent happens to reproduce
the maintainers' test. Measured on our corpus: applying the maintainers' own
merged fix changed the reported score on 3 of 153 tasks.

The repair is the one SWE-bench uses \cn: hold the tests out of the workspace
and inject them when grading. We precompute the post-patch content of each test
file at stage time and copy it over the workspace before the grader runs, rather
than applying a patch. Copying is deterministic and overwrites whatever the
agent wrote there, so weakening a test cannot raise a score.

\paragraph{Checks no submission can satisfy.} Two check families failed with the
reference fix in place.

The import check loaded a package-internal module as a detached top-level
module:
\begin{quote}\small
\texttt{spec = spec\_from\_file\_location('mod', src\_path); exec\_module(...)}
\end{quote}
Every relative import inside such a file raises
\texttt{attempted relative import with no known parent package}. It failed with
the reference fix applied on 37 of 59 staged tasks. Because the grader's overall
pass requires every check, those tasks were unsolvable by construction.

The second is subtler. Graders invoked \texttt{pytest} on a single file and
inherited the repository's own \texttt{addopts}. For a project with a coverage
gate this is fatal: with the fix applied and the held-out tests injected,
\texttt{arrow} reports \texttt{223 passed} and then
\texttt{FAIL Required test coverage of 99\% not reached}. Every test passes and
the grader records a failure.

\paragraph{Guards in the score.} 303 of the 374 checks across the admitted
corpus pass on an untouched workspace. They are not defective; they are guards
that detect deleted tests, wiped files and hardcoded shortcuts. The defect is
that they sat in the score. An empty submission earned a mean partial score of
0.815. We move guards out of the score rather than removing them: a submission
that trips one is reported inadmissible, and the score is computed over the
checks that fail on that task's pristine workspace. Discriminative status is a
property of a (task, check) pair and never of a check's name: ``source modules
import without error'' is a guard on one task and the entire point of another.

\section{\core{}}
\label{sec:core}

\paragraph{Construction.} For each task we check the upstream repository out at
its recorded base commit, install it in an isolated environment, and ask two
questions, following SWE-bench's fail-to-pass criterion \cn:
\begin{align*}
G_{\text{fail}} &: \text{the tests the patch adds fail without the source fix} \\
G_{\text{pass}} &: \text{the same tests pass with it}
\end{align*}
Both must hold. We record the resolved dependency set so staging never
re-resolves against whatever the package index serves later.

\paragraph{The ceiling is the honest denominator.} Of 631 tasks carrying a
repository and base commit, 229 (36\%) have a reference patch that adds a test.
The remaining 402 cannot be verified by a test signal, because the upstream pull
request never added one. Reporting the admitted count against 631 rather than
against 229 would make a sound corpus look broken.

\paragraph{Validation.} Each candidate is graded three ways: pristine, pristine
with the held-out tests injected, and with the full reference fix. A task is
admitted iff the second fails and the third passes.

\caption{Tasks that provably discriminate, over the same candidate set. The

\core{} is the 48 admitted tasks, drawn from 12 upstream repositories. Six of
seven admission gates pass on essentially every one of them: an empty submission
fails all 48, each has a non-empty discriminative set, and the upstream
reference scores 1.0 on 47 of 48.

The seventh gate fails, and we report it as a failure. It asks that at least
half of a grader's checks be discriminative; the measured median is 0.14.
Satisfying it would mean deleting anti-cheat checks, so we do not adjust it.
What it now measures is granularity rather than validity, and the number is
itself a result: with a median of one discriminative check per task, \core{} is
effectively pass/fail. The graded partial credit reported in the prior version
of this work was 81\% guard mass.

\section{Compute-matched coordination}
\label{sec:budget}

\paragraph{The confound.} Every comparison in the prior version ran the
conditions at different compute: a single agent at 20 model turns, a three-role
team at up to 140. Any difference so measured is confounded with a sevenfold
budget gap. We give every condition one shared turn allowance, consumed by
whichever role is acting.

\paragraph{Setup.} 48 tasks $\times$ 2 conditions $\times$ 3 budgets, one model,
seed 0. Solo receives the full specification; Full Team is
Planner/Executor/Verifier with enforced information partition.

\paragraph{At equal compute the team does not win.} Paired within task and
budget, the team solved one task the single agent failed, across 144
comparisons. Of 19 discordant pairs, 18 favour the single agent (exact
two-sided sign test, $p = 7.6\times10^{-5}$).

\paragraph{More compute makes it relatively worse.} The mean discriminative
deficit is $-0.104$, $-0.118$ and $-0.188$ at 20, 60 and 140 turns. ``The team
needs more compute'' is therefore not available as an explanation.

\paragraph{Teams damage the workspace more.} Guard violations rise
$1 \to 4 \to 8$ of 48 for the team against $1 \to 2 \to 3$ for the single agent.
At 140 turns 17\% of team runs deleted a test or wiped a file, against 6\% of
solo runs. Three roles means three hands editing a repository without seeing
what the others did. \todo{This is a mechanism claim; support it with the
failure taxonomy or soften it.}

\section{Related work}
\label{sec:related}

\paragraph{When a team should help, and when it should not.} The question of
whether dividing a task across agents improves the outcome is not new, and the
group performance literature answers it conditionally rather than affirmatively.
\citet{steiner1972group} organises group tasks by how individual contributions
combine and separates, among others, \emph{disjunctive} tasks, solved as soon as
one member solves them, from \emph{conjunctive} tasks, limited by the weakest
member. The prediction for disjunctive tasks is that a group adds little beyond
its strongest member, and the prediction for conjunctive tasks is that adding
members can reduce performance. A single-repository bug fix with a known failing
test is close to disjunctive: any agent that produces the right patch resolves
it.

Where coordination does pay, the literature locates the mechanism in what the
members know about each other rather than in the division of labour itself. A
transactive memory system, mutual knowledge of who knows what
\citep{wegner1987transactive}, is measurable
\citep{lewis2003measuring} and in software teams specifically is among the
sturdier correlates of performance \citep{faraj2000coordinating}. A second
mechanism applies when members hold genuinely different information and the
task requires pooling it \citep{stasser1985pooling}.

Two consequences matter for how a benchmark should be read. A benchmark whose
tasks are disjunctive should not be expected to show a team advantage, so a null
result there is weak evidence about coordination in general. And a protocol that
gives roles no way to learn each other's behaviour removes the mechanism by
which an advantage would arise, so a null result there is evidence about the
protocol rather than about role separation as an idea. We measure the second
condition directly rather than assuming it, in Section~\ref{sec:budget}.
\todo{Thompson's pooled/sequential/reciprocal interdependence taxonomy is the
cleanest fit to that measurement; the citation is not yet verified and is held
as a placeholder rather than cited from memory.}

\paragraph{Multi-agent LLM systems and their evaluation.} Frameworks that assign
roles to language model instances and route messages between them report gains
on software tasks \citep{chatdev2024,autogen2023}. Those role assignments are
specified by prompt: a single model is asked to behave as a planner, then as an
implementer. Nothing prevents the implementer from reading what only the planner
was meant to see, so a reported team score conflates following an instruction
with operating under a constraint. Evaluation suites for such systems have begun
to measure the process in addition to the outcome
\citep{multiagentbench2025}, and post-hoc analysis has assembled taxonomies of
how these systems fail \citep{cemri2025why}.

This work is complementary to that analysis and differs in direction.
\citet{cemri2025why} collects failures and organises them; we fix the compute
budget, enforce the information partition, and ask whether the division of
labour pays at all. Our contribution to that picture is not another taxonomy but
the prior question of whether the measuring device works, and one mechanism
measurement: the back-channel a transactive memory system would require exists
in our harness, is advertised in the role prompts, and carries 1.0\% of the
traffic.

\paragraph{Benchmark construction and the validity of the grader.} Agentic
coding benchmarks derived from merged pull requests share a construction in
which the tests that demonstrate a bug are withheld from the agent and supplied
by the harness at evaluation time, together with an explicit declaration of
which tests must fail before the fix and pass after it. \todo{SWE-bench and its
derivatives; citations pending verification.} Our audit shows that construction
is doing more work than it is usually credited for. It makes three of our five
criteria true by design, and corpora built outside that lineage do not inherit
them: our own is the case in point, failing every instance of the criterion that
a discriminating test be declared at all.

There is a growing literature on whether agentic benchmarks measure what they
claim. \todo{The ABC checklist for agentic benchmark design, and its reported
error rate on an established corpus, are directly relevant here; citation
pending verification.} Our audit is narrower and complementary: it is decidable
from task metadata without running a model, it reports an undecidable verdict
rather than guessing, and we report its false-positive rate before calibration,
which was 61\%.

\paragraph{What we take from this.} Two positions follow that we adopt rather
than argue for at length. The claim worth making about enforced role separation
is not that it measures collaboration, but that it separates prompt compliance
from structural constraint, which is narrower and checkable. And the claim worth
making about a null result is only as strong as the evidence that the instrument
could have detected a positive one, which is why the audit precedes the
experiment in this paper rather than following it.

\section{Limitations}

\paragraph{One model, and the second one does not yet agree.} The budget curve
above uses a single model at seed 0, so the sign test is over task-to-task
variation rather than over model or seed variation. A second model,
claude-sonnet-5, was run on the identical protocol. At 20 turns, the one budget
for which both conditions are complete, it shows \emph{no} team deficit: Solo and
Full Team each solve 4 of 48, the paired discriminative difference is $+0.000$,
and the discordant pairs split two each way. The 60 and 140 turn cells are not
reported because the API credential was rejected partway through each of them,
leaving 21 of 48 and 47 of 48 Full Team runs with no model response. Those runs
are recorded as zeros and we exclude them rather than average them: read
naively they would report a Full Team collapse to a raw mean of $0.019$
alongside the highest discriminative mean in the table, from 47 runs that never
reached the model and one that did. The dead runs are a contiguous suffix of the
run order, so the surviving subset is biased by task identity and cannot serve
as a reduced-$n$ estimate either. The compute-matched comparison is therefore
sound for one model at three budgets and a second model at one budget, and on
that evidence the honest reading is that the measurement instrument generalises
while the size, and possibly the sign, of the coordination effect may not.
\todo{Rerun the second model at 60 and 140 turns once a valid credential is
available; the affected cells are quarantined, not deleted.}

\paragraph{\core{} is small and narrow.} 48 tasks from 12 repositories, all
Python. The ceiling of 229 is itself limited by how often upstream maintainers
add a test with their fix. Repositories that build their own compiled
extensions (165 tasks, ceiling 53) and those whose installation pulls a deep
learning framework (94 tasks, ceiling 23) are excluded and would require
per-task container images.

\paragraph{Effectively pass/fail.} With a median of one discriminative check per
task, \core{} does not support graded partial credit. We report the
discriminative mean, but it is close to a pass rate.

\paragraph{A residual leak.} Task identifiers end in the upstream pull request
number. Renaming would invalidate every recorded result and run path, so we
record it instead. It is weaker than a URL: the model must resolve the reference
unaided. We removed 1061 explicit links to the fix pull request from the
documents the agents read.

\paragraph{Our own protocol found our own defects.} Every count in
Section~\ref{sec:inert} describes a benchmark we built and published. We do not
know how many of these conditions are present in benchmarks we did not build.
